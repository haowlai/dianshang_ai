### 1.1 表结构初始化核心逻辑 (init_db.py)
源码路径：[app/scripts/init_db.py](file:///d:/code/dianshang/app/scripts/init_db.py)

```python
"""
==============================================================================
数据库初始化脚本：app/scripts/init_db.py
原理：利用 SQLAlchemy 的 metadata.create_all 自动扫描所有继承 Base 的模型类并建表
==============================================================================
"""

import asyncio
import logging
from sqlalchemy import text
from app.core.database import engine
from app.models.base import Base

# 关键：必须显式导入所有 Model 模块，确保 SQLAlchemy 的 Base.metadata 能注册到所有表
import app.models.tenant
import app.models.user
import app.models.sku
import app.models.task
import app.models.task_node_run
import app.models.copy
import app.models.asset
import app.models.listing
import app.models.compliance
import app.models.knowledge
import app.models.provider
import app.models.batch
import app.models.log

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("init_db")

async def init_database():
    logger.info(">>> 正在连接数据库并检查扩展...")
    async with engine.begin() as conn:
        # 1. 确保 vector 向量扩展已启用
        logger.info(">>> 激活 PostgreSQL 向量扩展: vector")
        await conn.execute(text("CREATE EXTENSION IF NOT EXISTS vector;"))

        # 2. 一键创建所有在 models/ 下注册的 14 张实体表
        logger.info(">>> 正在基于 SQLAlchemy 2.0 Metadata 自动创建数据表...")
        await conn.run_sync(Base.metadata.create_all)

    logger.info(">>> [成功] 14 张业务数据表与 pgvector 扩展初始化完毕！")

if __name__ == "__main__":
    asyncio.run(init_database())
```

**运行命令**：
```bash
python -m app.scripts.init_db
```

## 二、生产环境数据库演进与 ALTER 变更语句汇总

在项目上线运营过程中，需求不断迭代，切忌直接删除数据库重新建表！必须编写增量 SQL 迁移变更语句（ALTER TABLE）。

### 2.1 业务迭代高频 ALTER 变更 SQL 清单

```sql
-- ==============================================================================
-- 变更批次 1：商品表 ac_sku 扩展字段
-- 需求：支持多币种价格计算、添加商品外部条形码与标签 JSONB 字段
-- ==============================================================================

-- 1. 添加货币类型字段 (默认美元 USD)
ALTER TABLE ac_sku ADD COLUMN IF NOT EXISTS currency VARCHAR(8) DEFAULT 'USD';

-- 2. 添加外部条形码/UPC编码，并添加索引
ALTER TABLE ac_sku ADD COLUMN IF NOT EXISTS barcode VARCHAR(64);
CREATE INDEX IF NOT EXISTS idx_sku_barcode ON ac_sku(barcode);

-- 3. 添加商品扩展属性标签 (JSONB 格式，支持GIN高效检索)
ALTER TABLE ac_sku ADD COLUMN IF NOT EXISTS extra_tags JSONB DEFAULT '{}'::jsonb;
CREATE INDEX IF NOT EXISTS idx_sku_extra_tags ON ac_sku USING gin(extra_tags);


-- ==============================================================================
-- 变更批次 2：任务运行表 ac_task_node_run 性能调优
-- 需求：快速根据 task_id 与 node_name 联合检索节点状态
-- ==============================================================================

-- 1. 为任务节点运行记录表增加组合索引（大幅提升前端 DAG 图轮询性能）
CREATE INDEX IF NOT EXISTS idx_node_run_task_node ON ac_task_node_run(task_id, node_name);

-- 2. 为节点运行时长增加索引，方便运维排查超时慢节点
CREATE INDEX IF NOT EXISTS idx_node_run_duration ON ac_task_node_run(duration_ms DESC);


-- ==============================================================================
-- 变更批次 3：合规质检表 ac_compliance 字段修改
-- 需求：修改风险等级字段长度，增加人工复核人字段
-- ==============================================================================

-- 1. 扩容字段长度
ALTER TABLE ac_compliance ALTER COLUMN risk_level TYPE VARCHAR(32);

-- 2. 增加复核人 ID
ALTER TABLE ac_compliance ADD COLUMN IF NOT EXISTS auditor_id VARCHAR(32);

-- 3. 增加复合查询索引
CREATE INDEX IF NOT EXISTS idx_compliance_task_pass ON ac_compliance(task_id, is_passed);
```

### 2.2 pgvector 向量索引构建与性能调优 (HNSW vs IVFFlat)

PostgreSQL 的 `pgvector` 支持两种向量索引类型：

| 索引类型 | 内存消耗 | 构建速度 | 查询速度 (QPS) | 召回准确率 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **IVFFlat** | 较小 | 极快 | 中等 | 约 95% | 数据量极巨大、内存受限 |
| **HNSW**（推荐） | 稍大 | 稍慢 | **极快 (微秒级)** | **> 99%** | **企业级标准、兼顾高准确率与低延迟** |

#### HNSW 索引创建与参数调优 SQL：

```sql
-- 1. 在 ac_knowledge 表的 1024 维 embedding 字段上创建 HNSW 余弦距离索引
CREATE INDEX IF NOT EXISTS idx_knowledge_embedding_hnsw 
ON ac_knowledge 
USING hnsw (embedding vector_cosine_ops)
WITH (
    m = 16,               -- 每个节点的最大双向链接数 (推荐 16 或 24)
    ef_construction = 64  -- 构建索引时的搜索深度 (推荐 64 或 128)
);

-- 2. 调整当前会话的检索精度参数 (ef_search 越大，召回率越高，耗时微增)
SET hnsw.ef_search = 40;
```

## 三、自动化备份与灾难恢复实操

### 3.1 PostgreSQL 自动化定时备份脚本 (带钉钉/企微告警)

创建自动化备份脚本 `/data/scripts/backup_postgres.sh`：

```bash
#!/bin/bash
# ==============================================================================
# PostgreSQL 自动化定时物理转储脚本
# 策略：每日凌晨 3:00 全量导出并 gzip 压缩，保留最近 7 天，自动清理过期文件
# ==============================================================================

BACKUP_DIR="/data/backups/postgres"
DATE=$(date +%Y%m%d_%H%M%S)
DB_NAME="agentic_commerce"
DB_USER="postgres"
DB_HOST="127.0.0.1"
DB_PORT="5432"
FILENAME="${BACKUP_DIR}/${DB_NAME}_${DATE}.sql.gz"

# 钉钉机器人 Webhook (可选，填入自己的 token)
WEBHOOK_URL="https://oapi.dingtalk.com/robot/send?access_token=your_token"

mkdir -p $BACKUP_DIR

echo "[$(date)] 开始执行数据库备份: $DB_NAME..."

# 使用 pg_dump 全量导出并直接管道送给 gzip 高压缩比压缩
PGPASSWORD="postgres" pg_dump -h $DB_HOST -p $DB_PORT -U $DB_USER $DB_NAME | gzip > $FILENAME

if [ $? -eq 0 ]; then
    FILE_SIZE=$(ls -lh $FILENAME | awk '{print $5}')
    echo "[$(date)] 备份成功！文件: $FILENAME，大小: $FILE_SIZE"

    # 清理 7 天前的过期备份
    find $BACKUP_DIR -name "*.sql.gz" -mtime +7 -exec rm -f {} \;

    # 发送通知 (成功)
    curl -s -H "Content-Type: application/json" -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"[DB备份通知] $DB_NAME 备份成功！大小: $FILE_SIZE\"}}" $WEBHOOK_URL > /dev/null
else
    echo "[$(date)] 备份失败！"
    curl -s -H "Content-Type: application/json" -d "{\"msgtype\":\"text\",\"text\":{\"content\":\"[DB备份告警] $DB_NAME 备份失败，请立即排查！\"}}" $WEBHOOK_URL > /dev/null
    exit 1
fi
```

**配置 Crontab 定时任务**：
```bash
chmod +x /data/scripts/backup_postgres.sh
crontab -e
# 添加以下一行（每天凌晨 03:00 自动执行）：
0 3 * * * /bin/bash /data/scripts/backup_postgres.sh >> /data/backups/postgres/backup.log 2>&1
```

### 3.2 备份恢复与回滚 SOP 操作流程

当生产发生误删或数据污染时，按以下 SOP 快速恢复：

```bash
# 1. 停止上层应用，防止新数据写入造成不一致
sudo systemctl stop agentic-backend

# 2. 解压并导入指定的备份文件
gunzip < /data/backups/postgres/agentic_commerce_20261006_030000.sql.gz | psql -h 127.0.0.1 -U postgres -d agentic_commerce

# 3. 验证关键表数据记录量
psql -h 127.0.0.1 -U postgres -d agentic_commerce -c "SELECT count(*) FROM ac_sku;"

# 4. 重新拉起应用
sudo systemctl start agentic-backend
```

## 四、高可用服务巡检与监控脚本

### 4.1 服务器资源与容器健康巡检 Shell 脚本

编写巡检脚本 `/data/scripts/health_check.sh`：

```bash
#!/bin/bash
# ==============================================================================
# 系统资源与关键进程探针
# 监控：磁盘占用 > 85%、内存占用 > 90%、后端服务端口与进程存活
# ==============================================================================

# 1. 检查磁盘占用
DISK_USAGE=$(df -h / | awk 'NR==2 {print $5}' | tr -d '%')
if [ $DISK_USAGE -gt 85 ]; then
    echo "⚠️ [告警] 磁盘占用过高: ${DISK_USAGE}%"
fi

# 2. 检查内存占用
MEM_USAGE=$(free | awk '/Mem:/ {printf "%.0f", $3/$2 * 100}')
if [ $MEM_USAGE -gt 90 ]; then
    echo "⚠️ [告警] 内存占用危险: ${MEM_USAGE}%"
fi

# 3. 检查后端核心端口 8002 探针
curl -s -f http://127.0.0.1:8002/health > /dev/null
if [ $? -ne 0 ]; then
    echo "🚨 [严重告警] FastAPI 8002 探活失败！尝试自动重启服务..."
    sudo systemctl restart agentic-backend
fi
```

## 五、数据库与运维高频故障应急预案

| 故障现象 | 根因定位 | 快速处置应急命令 |
| :--- | :--- | :--- |
| **FATAL: remaining connection slots are reserved for non-superuser connections** | 数据库连接池被打满 | 登录 psql 执行 `SELECT * FROM pg_stat_activity WHERE state = 'idle';` 查看空闲占用，并增加 `max_connections = 300`。 |
| **数据库出现锁等待与超时** | 多个事务并发更新同一记录产生锁冲突 | 执行 `SELECT pid, query, age(clock_timestamp(), query_start) FROM pg_stat_activity WHERE wait_event_type = 'Lock';`，通过 `SELECT pg_terminate_backend(pid);` 强制杀死死锁进程。 |
| **MinIO 磁盘写满导致生成失败** | 大模型生成的高清图片/视频累积过多 | 配置 MinIO 生命周期规则 (ILM)，设置临时生成的素材 30 天后自动归档或清理。 |
