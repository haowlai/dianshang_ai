# 架构风格与总体策略

## 2\.1 架构风格

本系统采用“分层架构 \+ 多智能体编排 \+ 事件驱动”的混合架构风格。

- 分层架构：后端采用 FastAPI 分层模式，划分为路由层、服务层、数据访问层与公共层，确保职责单一、依赖方向明确。

- 多智能体编排：核心业务由 LangGraph 状态图驱动的 7\-Agent 协作流水线完成。LangGraph 将智能体建模为状态图，节点是计算单元，边是路由逻辑，状态是贯穿全图的共享内存。

- 事件驱动：任务进度、Agent 节点状态、LLM 调用事件通过 WebSocket 实时推送至前端可观测工作台。

## 2\.2 多智能体架构选型依据

2026 年，智能体开发已从“Prompt \+ 工具调用”的简易编排演变为融合原生模型能力、持久化记忆、多智能体协作的系统工程。传统单体 Agent 存在三大致命缺陷：认知过载导致指令冲突、调试黑盒难以定位问题、成本失控。因此，本系统采用多智能体系统（MAS）架构，通过“路由 \+ 执行者”模式实现专业分工。

LangGraph 相较于传统 LangChain Chain 的核心优势在于：状态驱动、图结构、可中断、可恢复、可监控。系统采用 P\-E\-V（规划\-执行\-验证）循环的图结构变体，工作流从编排调度开始，经需求分析、创意策划、视觉设计，分支到图片/视频生成，最终由质量审核验证并决策路由。

### 4\.2\.2 AgentState 状态定义

`AgentState` 是 LangGraph 状态图的共享状态，所有节点读取并更新其中字段。采用 `TypedDict` 定义，使用归约器控制并发更新行为。

### 4\.2\.3 Agent 基类设计

所有 Agent 继承自统一 `BaseAgent` 抽象基类，确保一致的行为模式：

```Plain Text
BaseAgent (ABC)
├── __init__(model: str)
├── _build_prompt() -> ChatPromptTemplate   [抽象方法]
├── execute(state: dict) -> dict             [抽象方法]
└── _get_llm(temperature: float) -> LLM     [延迟加载]
```

职责分离：`_build_prompt()` 负责提示词模板构建，`execute()` 负责核心逻辑，`_get_llm()` 负责 LLM 实例延迟初始化。

### 4\.2\.4 条件路由设计

系统包含两处条件路由：

路由一：媒体类型路由（VisualDesigner 之后）

路由二：质量审核路由（QualityReviewer 之后）

条件边基于当前 State 的实时值动态决定目标节点，支持分支、循环重试、异常回滚。

### 4\.2\.5 Checkpoint 与持久化

工作流使用 Checkpoint 机制保存执行状态：

- 开发环境：`MemorySaver`（内存级，快速迭代）

- 生产环境：`PostgresSaver`（持久化，支持断点恢复）

每个 `thread_id` 对应一个独立的执行会话，支持 `interrupt()` 人工介入与 `resume()` 恢复执行。

## 5\.3 RAG 检索流程（以 RequirementAnalyzer 为例）

```Plain Text
RequirementAnalyzer 需要品牌规范洞察
    │
    ▼
构建检索查询: "品牌调性 合规要求 类目知识"
    │
    ▼
Query 预处理: 短查询扩充 (HyDE)
    │
    ▼
Embedding 编码: text-embedding-v4 → 1024维向量
    │
    ▼
pgvector 相似度检索:
    SELECT content, metadata, 1 - (embedding <=> query_vec) AS score
    FROM ac_knowledge_chunk
    WHERE tenant_id = :tenant_id
      AND doc_type IN ('brand_guide', 'compliance_rule', 'category_knowledge')
    ORDER BY embedding <=> query_vec
    LIMIT 5
    │
    ▼
阈值过滤: score >= 0.5
    │
    ▼
Reranker 重排序 (可选)
    │
    ▼
返回命中分块 → 注入 LLM Prompt
```

```Plain Text
    │       ▼
    │   retry_count < max_retries?
    │       ├── 是 → 路由到 CreativePlanner 重做
    │       └── 否 → 路由到 END，标记失败，提示人工介入
    │
    └── 未命中红线 → 质量评分
            │
            ▼
        overall_score >= 阈值?
            ├── 是 → passed = true → END
            └── 否 → passed = false, 低分预警
                     │
                     ▼
                retry_count < max_retries?
                     ├── 是 → 路由到 CreativePlanner
                     └── 否 → END (标记失败)
```

## 8\.2 环境配置策略

系统支持两种运行模式：

1. 开发环境：仅基础设施（PostgreSQL、Redis、MinIO）容器化，后端与前端在宿主机本地运行，利用热重载提升开发效率。基础设施数据直接映射到项目 `data/` 目录，方便查看。

## 9\.2 日志架构设计

本系统采用“分层日志 \+ 全链路追踪”的设计，日志不依赖单一中间件，而是按职责拆分到不同层级。

全链路追踪机制：

1. `RequestContextMiddleware` 在请求入口生成 `request_id` 和 `trace_id`，写入 `contextvars`。

2. 服务层、Repo 层、Agent 节点通过 `logging` 框架自动携带 `trace_id`。

3. LangGraph 节点执行时，读取 `trace_id` 并写入 `TaskNodeRun` 表。

4. WebSocket 推送事件时，携带 `trace_id`，前端工作台按 `trace_id` 关联展示。

5. OpenTelemetry 自动插桩，生成 Span，贯穿 HTTP → Service → Agent → LLM。

日志规范：

- 所有日志统一 JSON 格式，便于 ELK / Loki 采集。

- 日志中禁止输出密码、API Key、完整请求体等敏感信息。

- 访问日志、业务日志、Agent 日志默认保留 7 天；审计日志保留 ≥30 天。

- 日志级别：DEBUG（开发）、INFO（生产）、WARN、ERROR。

- 关键路径（任务创建、工作流执行、合规阻断）必须打 INFO 及以上日志。

# FastAPI 中间件设计

## 10\.1 设计结论

本系统采用“核心中间件 \+ 内置中间件 \+ 依赖注入 \+ 服务层下沉”的组合策略。

自研核心中间件只保留 2 个，其余能力分别由内置中间件、依赖注入、全局异常处理器、服务层和 OpenTelemetry 承接。

## 10\.2 横切关注点归属映射

## 10\.3 核心中间件职责

### 10\.3\.1 RequestContextMiddleware

- 读取或生成 `X-Request-ID`；

- 生成 `trace_id`，用于 OpenTelemetry 与 Agent 可观测；

- 尝试解析 JWT，写入 `tenant_id`、`user_id`、`role`；

- 同时写入 `request.state` 与 `contextvars`；

- 响应头返回 `X-Request-ID`；

- 只做“预解析”，不强制阻断，强制认证交给依赖注入。

### 10\.3\.2 GlobalGuardMiddleware

- 添加安全响应头；

- 基于 Redis 做限流；

- 检查 `Content-Length`，限制请求体大小；

- 可选：租户配额检查；

- 可选：`Idempotency-Key` 幂等控制；

- 超限返回 429、413 或 402。

## 10\.4 中间件执行顺序

从外到内建议为：

1. ServerErrorMiddleware

2. HTTPSRedirectMiddleware

3. TrustedHostMiddleware

4. CORSMiddleware

5. RequestContextMiddleware

6. GlobalGuardMiddleware

7. GZipMiddleware

8. ExceptionMiddleware

9. Router → 依赖 → 路由函数

注意：Starlette 中间件遵循“洋葱模型”。`app.add_middleware()` 是向栈内插入，后添加的中间件位于外层，在请求阶段最先执行。因此，代码中添加顺序与请求执行顺序相反。建议按“从内到外”的逻辑添加：先添加希望最晚接触请求的中间件，最后添加希望最先接触请求的中间件。

```Python
from fastapi import FastAPI
from starlette.middleware.cors import CORSMiddleware
from starlette.middleware.gzip import GZipMiddleware
from starlette.middleware.trustedhost import TrustedHostMiddleware
from starlette.middleware.httpsredirect import HTTPSRedirectMiddleware

app = FastAPI(title="AgenticCommerce")

# 按从内到外添加
app.add_middleware(GZipMiddleware, minimum_size=1000)  # 最内层，最后处理请求
app.add_middleware(GlobalGuardMiddleware)              # 中间层
app.add_middleware(RequestContextMiddleware)           # 最外层，最先拦截请求

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.CORS_ORIGINS,
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=settings.TRUSTED_HOSTS,
)

if settings.ENV == "prod":
    app.add_middleware(HTTPSRedirectMiddleware)
```

## 10\.6 验收标准

- 每个请求有唯一 `request_id`，响应头返回 `X-Request-ID`。

- `tenant_id`、`user_id`、`trace_id` 在服务层、Repo 层、Agent 节点可读取。

- 限流生效，超限返回 429；请求体超限返回 413。

- 安全响应头、CORS、TrustedHost 生效。

- 认证与角色权限由依赖注入完成，不由中间件完成。

- 统一错误响应由全局异常处理器完成。

- WebSocket 单独鉴权，禁止跨租户订阅。

- OpenTelemetry Trace 贯穿 HTTP → Service → Agent → LLM。

- 中间件不破坏流式响应、文件下载与 OpenAPI 文档。
